## 最新使用者偏好

GitHub bot／Slack GitHub integration、依賴更新、CI 與例行維護不是新聞；採集前、既存資料
選稿前與輸出前都套用 automation 排除。正式站曾出現的 5 篇自動通知已依使用者要求撤下。
GitHub 僅接收具體成果、協作邀請或對使用者有實質影響的人工內容。

## 架構決策

依使用者要求透過 Claude CLI 再次諮詢，採納：安全政策獨立於可還原資料庫、保守主題合併、
unknown 發送不盲重試、來源增量有界、影子評分不自動升級，以及 Docker 掛載 data 父目錄後
原子切換 site symlink。既有文章 ID／RSS GUID 保持不變。異地備份依最新使用者指示省略。

## 2026-09-19 Notion 來源發現（#15）

Code for Japan 已同意以其公開 Notion 入口作為來源發現對象。入口的專案資料庫取出 18 個
repository，逐一以 GitHub 官方 API 核對後採用 90 天內有 push 的八個，其餘十個休眠者記錄原因。

發現刻意與發布隔離：不在 `collect`／`report`／`run` 的路徑上，不寫入允許清單，端點壞掉
只是不再有新建議。只讀取傳入的那一頁，因為巡迴子頁面只多找到一個 repository，
代價卻是讀取 348 列的成員名錄與活動參加紀錄，而屬性型別擋不住那些欄位。

預算的結論來自實測而非估計：Slack 定常每輪 9 次而非用滿 40，十個 repository 每輪約 50〜63 次，
每輪預算 80 夠用。真正的限制是 `github.get` 未送 `Authorization`，未認證上限每小時 60 次，
十個 repository 就要 41 次；實測一輪有六個 repository 被限流。加入可選 token 後零限流，
日預算則從 1,500 提高到 1,800。

自動化發現卻沒有自動化記錄會產生新問題：被人判斷為不納入的 repository 會每週重複提案。
改為同時檢查既有的排除台帳（`exclusion --scope container`），不另開第二份清單。

## 2026-09-19 第二輪驗收修正

- 採集限制是 HTTP 請求數（每輪 80、每日 1,500），不是模型費用額度。遇到次數上限的
  頻道下輪優先補抓；沒有真的發出請求就不更新嘗試時間。每頻道分頁共享剩餘次數，保留
  未完成游標；429 等遠端限制仍遵守退避。root 失敗在等待重試期間不假裝恢復健康。
- 上游 PHP 處理微秒參數會損失精度，已實測重現。HTTP 使用較寬的整秒邊界，程式以
  Decimal 精確去重／比對，補回 GIS exact root；同秒頁面無法前進時明確保留缺口。
- 雲林原文及 GIS 轉貼已重新以公開 API 核實。已發布空主文恢復時會建立一次「本報更正」，
  原文與轉貼接回既有主題，保留 post 4 與送達紀錄，避免把本報補正描述成作者新公告。
- 補譯排程每輪最多 3 篇、每篇最多 2 次模型請求，具退避、持久化次數及 6 輪自動重試上限。
  保存時交易內檢查退出與原文字串，合併其他執行程序已保存的有效語言，不重送舊文章。
- writer 契約為 `grounded-four-locale-v4`；閉門回覆不能重貼舊報名邀請，介紹網址不推定為
  報名網址，明示參與方式的長 URL 保存為結構化證據。補正標題及日韓來源歸屬有固定案例。
- #2 的兩週條件只計目前版本的 shadow 紀錄；active 或其他版本不能灌入觀察期。
  #2、#6 的真實兩週比較尚未滿期，不能只憑測試通過就關閉。其他項目依各自驗收條件判定。
